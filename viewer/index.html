        How to use
        
        
      
        
      
        
        
        
        
        
        
        
      
        
      
        

        
        
          
        End-to-end flow
        
          
          
            
        1. Capture a session on the worker machine: tray app polls active window, fires marker events on hotkey or tray, optionally drives OBS to record the screen.
          2. 
            
        2. Move the session folder to the analyst's machine (network share, USB, however you already move OBS recordings).
          3. 
            
        3. Open the session in this viewer: Session view → Open session folder...
          4. 
            
        4. Analyze: click Analyze session. Tick Build process map to also discover a BPMN diagram.
          5. 
            
        5. Annotate: rename markers, add timestamped notes. Edits save to annotations.json; raw events stay immutable.
          6. 
          
        
          
        What the viewer expects in a session folder
        
          
          
            
        • events.jsonl - one JSON event per line; the durable artifact
          • 
            
        • manifest.json - session metadata + OBS recording reference
          • 
            
        • screenshots/ - event-triggered captures, optional
          • 
            
        • obs/sync.json - tracker↔OBS time offset, optional
          • 
            
        • After normalization: events.xes, events.csv, stats.json, process_map.bpmn, dfg.json
          • 
          
        
        
        

        
        
          
        Session view layout
        
          
          
            
        • Video pane (top left): OBS recording if linked in the manifest. Standard HTML5 controls; click any timeline event to seek.
          • 
            
        • Minimap (above the timeline): 30-px strip showing the whole session compressed. Click anywhere to jump; drag the highlighted viewport to scroll. Stays in sync as you zoom.
          • 
            
        • Timeline (top right): activity bands (per-app colour), idle gaps (grey), marker bars, screenshot dots (hover for a thumbnail preview), event-density histogram, optional per-step bands and numbered note dots beneath. Right-click an activity band for the context menu (insert markers / scope to case). Shift-drag across the background to select a time range: a stats card pops above the legend with duration, event count, marker count, screenshot count, and top apps in the range. Esc clears the selection.
          • 
            
        • Snap-to-event: clicking the timeline background snaps to the nearest event within ~10px tolerance; click in genuine empty space to seek to the literal point.
          • 
            
        • Persistent zoom + scroll: each session remembers its zoom factor and scroll position in localStorage. Reopening a session restores where you were.
          • 
            
        • Annotations (right column) with three sub-tabs:
              
            
                
          • Notes - pin text to the current playback time
            • 
                
          • Screenshots - thumbnail grid; click to seek the video
            • 
                
          • Markers - full list; double-click a Start marker to rename it (edit saved to annotations.json)
            • 
              
          
            
          • 
            
        • Raw events (collapsible at the bottom): filter by text or by type checkboxes. Click any row to seek, or use its per-row actions to jump, spin off a new step, or add the event to the selected step.
          • 
          
        
          
        Working with markers
        
          
        Markers bracket business activities. Captured markers are immutable in events.jsonl; edits live in annotations.json and are layered in by re-normalization (§9.3).
        
          
        Markers are not cases. During capture the worker places markers: a start, an end, and a label. Cases (the individual runs through the process) are never recorded directly: they're derived from the marker stream during normalization, with nested markers forming a case tree. That's why editing a marker reshapes the cases, and why there is no "mark a case" action while recording: you mark markers, and the pipeline computes the cases from them.
        
          
        From the Markers sub-tab on the right:
        
          
          
            
        • Rename: double-click a Start marker row, type the new label, press Enter.
          • 
            
        • Adjust timestamp: hover a row, click the clock icon. Sets the marker's timestamp to the current video time (or prompts for an ISO timestamp if there is no video).
          • 
            
        • Delete: hover a row, click the X icon. The marker is dropped from the normalized stream; raw events stay untouched.
          • 
          
        
          
        To add a marker, right-click the Flow timeline at that moment and choose Insert Start marker here or Insert End marker here.
        
          
        Every marker change shows at once in the list and on the timeline, marked pending. Click Analyze to apply on the actions bar (or Analyze session) to apply it to the cases, steps, statistics and exports.
        
          
        Moving, inserting and deleting markers is enough to merge or split cases. To merge two adjacent same-label cases, delete the inner End and the following Start. To split a long case, move its End earlier and insert a new Start after it.
        
        
        

        
        
          
        Flow and Steps
        
          
        At the top of every loaded session you'll see a View bar. Flow and Steps show the same captured data at two levels of detail:
        
          
          
            
        • Flow: raw events as they were captured. Use this to understand what actually happened, second-by-second. Video, timeline, screenshots, notes.
          • 
            
        • Steps: each run's steps. A "step" is one named thing the worker did: Search customer in Salesforce is one step, even if it took 14 clicks underneath.
          • 
          
        
          
        Runs and drafted steps
        
          
        A run is one pass through the process, from a start marker to its end marker (the capture app's run hotkey places them). When you click Analyze session, the app drafts every run's steps: a step is one visit to a screen, and it ends at the action that commits the work there (Save, Search, Submit, Send) or where the worker moves to another screen. The Steps view lists the runs in time order; open a run to see its steps. Steps that fall outside every run are listed under Outside runs.
        
          
        Confirm the pattern run first
        
          
          
            
        1. Open the pattern run: the first run, marked Pattern (Use as pattern picks another one).
          2. 
            
        2. Check its steps against the video or the screenshots. Where a boundary is wrong, merge, split, add or hide steps (right-click a step, or use the step editor).
          3. 
            
        3. Give the steps the names you want in the document: double-click a name, or select the step and press Enter.
          4. 
            
        4. Click Confirm run: the steps you did not change are accepted as they are.
          5. 
          
        
          
        While you confirm it, the app counts the boundary fixes you make to the pattern run: merges, splits, added steps, and hidden or deleted drafts. Renames are not counted, and Ctrl+Z takes a fix back. Once the run is confirmed it shows one line, for example Run 1: 12 drafted steps, 2 boundary fixes (merge 1, split 0, add 1, drop 0); Copy puts that line on the clipboard.
        
          
        Names are remembered
        
          
        When you rename a drafted step, the matching drafted steps in the other runs (the same screen and the same closing action) take the name at once, and the name is remembered on this computer: the next analysis, of this session or of a later one, drafts those steps with it. Such a step shows a small remembered tag. The name box suggests remembered names and the names already used in the session.
        
          
        What the step labels mean
        
          
          
            
        • Draft drafted by the app and not checked yet. Every analysis drafts it again.
          • 
            
        • Confirmed you accepted the draft as it is (Confirm run). Every analysis keeps it.
          • 
            
        • Edited you changed the step: its name, its boundaries or its flags. Every analysis keeps it.
          • 
            
        • Added you added the step by hand. Every analysis keeps it.
          • 
            
        • Hidden you took the step out as noise. It stays out of the list (Show hidden steps on its run lists it again), and every analysis keeps it out.
          • 
          
        
          
        A run reads Draft while it still has drafted steps, and Confirmed once every step in it is confirmed, edited or added.
        
          
        Cutting down step noise
        
          
          
            
        • Ignored apps (toolbar button): tick the apps that aren't part of the process (they're left out of the drafting entirely), and the session re-analyzes. The choice is saved per session, so a re-analysis keeps them out.
          • 
            
        • Hide as noise (step editor or right-click): take a single step out. Unlike delete, a hidden step survives re-analysis: an analysis won't bring it back.
          • 
            
        • Delete selected: tick (or Ctrl+click) two or more steps, then delete them all in one go (Ctrl+Z restores). The next analysis drafts a deleted drafted step again.
          • 
          
        
          
        Flags
        
          
        A step can be flagged as Waste: it shouldn't be needed (rework, duplicate effort, fixing someone else's mistake). The flag doesn't change the data, but it shows up in exports and statistics.
        
          
        Branches, exception paths and automation candidates are not flags: they come from the recorded runs (the map's branches, the runs that differ, and step sequences that repeat).
        
        
        

        
        
          
        Running a capture session
        
          
          
            
        1. (One-time) Launch OBS with WebSocket enabled (Tools → WebSocket Server Settings → Enable, port 4455).
          2. 
            
        2. (Optional) Set PDT_CONFIG=path\to\your-config.yaml to load engagement-specific labels, hotkeys, OBS settings. See capture/sample-config.yaml.
          3. 
            
        3. Launch the capture tray app (npm start in capture/).
          4. 
            
        4. Right-click the tray icon → Start capture session. Or just press the run hotkey: the session auto-starts.
          5. 
            
        5. Show the status window (tray menu) for the live dashboard.
          6. 
            
        6. Press the run hotkey at the start of each run as the SME walks through the process. End the session when done.
          7. 
          
        
          
        Default hotkeys
        
          
        
            
        Ctrl+Shift+SStart the next run (Run 1, Run 2, ...). Ends the previous run first. Starts the session if none is running.
        
            
        Ctrl+Shift+EEnd the current run.
        
            
        Ctrl+Shift+PManual screenshot, annotated as screenshot_manual.
        
          
        
          
        All three are overridable in config.yaml under hotkeys:.

        Click behaviors
        
          
          
            
        • Any timeline band, marker, screenshot dot, or event row → seek the video
          • 
            
        • Right-click an activity band on the timeline → context menu: insert a Start/End marker at the clicked moment, scope view to the case under the cursor, jump to the case start / end. A faint ⋯ appears on hover to advertise the menu.
          • 
            
        • Marker row in the sidebar → seek; double-click a Start marker → rename
          • 
            
        • Recent session in the empty state → reload that session
          • 
          
        
          
        Cancelling a long analysis
        
          
        Once an analysis kicks off the log host opens automatically. A red Cancel button in the log summary stops the in-flight Python child (graceful first, hard kill 500ms later). It works for Analyze session.
        
        
        

        
        
          
        Common issues
        
          
        
            
        Normalization fails with "normalize.py not found"
        
            
        The viewer expects normalization/ as a sibling of viewer/ in dev, or under resources/normalization/ in a packaged build. Override with PDT_PYTHON if needed.
        

            
        "ModuleNotFoundError: pm4py" during normalization
        
            
        Run pip install -r normalization/requirements.txt against the Python interpreter the viewer uses.
        

            
        BPMN map shows "bpmn-js failed to load"
        
            
        The BPMN file is still on disk under the session folder - importable into Adonis directly. The in-viewer preview is a nice-to-have.
        

            
        No video in session view
        
            
        Capture ran without OBS, or the OBS recording path in manifest.json is unreachable. Timeline + statistics still work; click-to-seek is just a no-op.
        

            
        Empty event table
        
            
        Check the type checkboxes (activity / marker / system) and clear the text filter.
        

            
        Hotkey didn't register in capture
        
            
        Another app may have the same global shortcut. Enable PDT_DEBUG=1 in the capture launch env and check %APPDATA%\process-discovery-tracker\boot.log for "hotkeys: start=false". Edit your config.yaml to use different keys.
        

            
        Citrix or remote-desktop session shows one band labelled "Citrix Workspace.exe"
        
            
        active-win cannot see inside Citrix windows from the local host. Either run the capture tracker inside the Citrix session, or accept that local capture will not classify inner apps and rely on markers + the OBS video for context.
