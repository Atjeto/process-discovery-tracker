        Process Template
        
          
        A reusable definition of an expected process — its steps, phases, and the case anchor (the field that identifies each ticket/order) — that future sessions can auto-match against instead of getting generic step suggestions.
        
          
        
            ▸ How this works
            
        A Process Template is a reusable definition of an expected process: its steps, phases, the UI patterns that identify each one — and the case anchor (the field that identifies each ticket/order) that splits a session into cases. When you load a template here, captured sessions can be auto-matched against it instead of getting generic step suggestions. Templates are how you turn "a recording of someone working" into "a recording of this specific process, with the steps named correctly."
        
            
        The primary way to make one is as a byproduct of curation: open a session, curate its steps, then Steps → Export as Process Template. The export carries each step's match rules and the confirmed case anchor (the field that identifies each ticket/order), so the next session of the same process arrives with its cases already identified and its steps auto-matched. The list below stays directly editable; the raw YAML and version compare live in the Machine layer at the bottom.

Each becomes a step with a match rule derived from its interactions — linked to your App Library where a matching entry exists. For precise per-step rules, use Match rules… on each step instead.

        App Library
        
          
        Each app you record gets one vocabulary file mapping its UI elements to meaningful names — optional, and worth building when you'll record the same process again.
        
          
        
            ▸ How this works
            
        Each app you record gets one vocabulary file that maps its UI elements (Save button, Search field, etc.) to meaningful names. The names roll into step names automatically on every future session that touches the app. Edit them as a form here - no YAML required.
        
            
        This is optional. Reading a recording you've received needs nothing here — the Overview summary, findings, and step groups stand on their own. A vocabulary pays off when you'll record the same process again: name an app once and every later recording of it reads better. Start one from a recording you already have (no live app needed) with Start from a recording… below.
        
            
        Underlying storage is YAML at normalization/app_vocabularies/. You can edit those files directly if you prefer, or use this form. Both write to the same place.

          How to use
          
        
      
          
      
          
        
        
        
        
        
        
        
        
      
          
      
          

        
          
          
          End-to-end flow
          
          
            
            
          1. Capture a session on the worker machine: tray app polls active window, fires marker events on hotkey or tray, optionally drives OBS to record the screen.
            2. 
            
          2. Move the session folder to the analyst's machine (network share, USB, however you already move OBS recordings).
            3. 
            
          3. Open the session in this viewer: Session view → Open session folder...
            4. 
            
          4. Analyze: click Analyze session. Tick Build process map to also discover a BPMN diagram.
            5. 
            
          5. Annotate: rename markers, add timestamped notes. Edits save to annotations.json; raw events stay immutable.
            6. 
            
          6. Compare across sessions (Tab 2) when you want statistics, path variations, and a combined process map.
            7. 
          
          
          
          Save your work as a project
          
          
          The top-bar Project menu bundles the session set you've loaded for comparison, the focus session, the active Process Template, the current view mode, and the case scope into a single .pdt-project.json file. Use it when you're juggling multiple sessions and a template across days — instead of re-loading everything every morning, pick the project from Recent projects on the empty state.

            •

            •

            •

            • Notes - pin text to the current playback time
              • 
                
            • Screenshots - thumbnail grid; click to seek the video
              • 
                
            • Markers - full list; double-click a Start marker to rename it (edit saved to annotations.json)
              • 
              
            
            
            • 
            
          • Raw events (collapsible at the bottom): filter by text or by type checkboxes. Click any row to seek, or use its per-row actions to jump, spin off a new step, or add the event to the selected step.

          Working with markers
          
          
          Markers bracket business activities. Captured markers are immutable in events.jsonl; edits live in annotations.json and are layered in by re-normalization (§9.3).
          
          
          Markers are not cases. During capture the worker places markers — a start, an end, and a label. Cases (the individual runs through the process) are never recorded directly: they're derived from the marker stream during normalization, with nested markers forming a case tree. That's why editing a marker reshapes the cases, and why there is no "mark a case" action while recording — you mark markers, and the pipeline computes the cases from them.
          
          
          From the Markers sub-tab on the right:
          
          
            
            
          • Rename: double-click a Start marker row, type the new label, press Enter.
            • 
            
          • Adjust timestamp: hover a row, click the clock icon. Sets the marker's timestamp to the current video time (or prompts for an ISO timestamp if there is no video).
            • 
            
          • Delete: hover a row, click the X icon. The marker is dropped from the normalized stream; raw events stay untouched.
            • 
          
          
          
          After any edit, click Analyze session again to push the change into XES, CSV, and statistics.
          
          
          Boundary adjustment + delete give you everything needed to merge or split cases in practice. To merge two adjacent same-label cases, delete the inner End and the following Start. To split a long case, adjust its End earlier and (with a future UI) insert a new Start - for now you can edit annotations.json directly until that lands.
          
        
          

        
          
          
          Three views of the same session
          
          
          At the top of every loaded session you'll see a View bar with three buttons. They show the same captured data at different levels of abstraction:
          
          
            
            
          • Flow: raw events as they were captured. Use this to understand what actually happened, second-by-second. Video, timeline, screenshots, notes.
            • 
            
          • Steps: the same data grouped into logical actions. A "step" is what a process analyst would call one named thing the worker did. Search customer in Salesforce is one step, even if it took 14 clicks underneath.
            • 
            
          • Phases: steps grouped into milestones. A "phase" is what an exec would call one chunk of the process. Validate customer is a phase that contains the Search step, the Credit check step, and the KYC step.
            • 
          
          
          
          How steps get created
          
          
          You have three choices and you don't have to pick one:
          
          
            
            
          1. Auto-suggested: normalize.py walks the interaction stream and splits on idle gaps, app switches, and window changes. Cheap and works on any session. Quality depends on how clean the workflow was.
            2. 
            
          2. Auto-matched: if you've loaded a Process Template, every captured interaction is tested against the template's match rules. Matched interactions roll up into steps that get the template's names. Much better quality, but only works for processes you've templated.
            3. 
            
          3. Manually authored: click + Add manual step in the Steps view and define one yourself. Useful for the long tail of processes that don't have a template yet.
            4. 
          
          
          
          What state means
          
          
          Every step has a colored dot indicating where it came from:
          
          
            
            
          •  auto-suggested - an automatic guess from the interactions. Replaced on every re-analysis.
            • 
            
          •  auto-matched - matched a Process Template. Replaced when you re-match against a newer template version.
            • 
            
          •  manually authored - you typed it. Survives re-normalization.
            • 
            
          •  edited - you modified an auto-suggested or auto-matched step. Survives re-normalization.
            • 
            
          •  hidden - you suppressed it as noise. It stays out of the list and survives re-normalization.
            • 
          
          
          
          Cutting down step noise
          
          
          A session captured with a screen recorder or other background app open can produce dozens of irrelevant steps ("OBS: 12 interactions"). Three tools handle this:
          
          
            
            
          • Ignored apps (toolbar button): tick the apps that aren't part of the process — they're left out of step suggestion entirely, and the session re-analyzes. The choice is saved per session, so re-analyze keeps them out.
            • 
            
          • Delete selected: tick (or Ctrl+click) two or more steps, then delete them all in one go (Ctrl+Z restores).
            • 
            
          • Hide as noise (step editor): suppress a single step. Unlike delete, hidden steps survive re-normalization — a re-analyze won't bring them back. Reveal them via the hidden filter chip.
            • 
          
          
          
          Flags
          
          
          Each step can be tagged. These don't change the data but they show up in exports and statistics:
          
          
            
            
          • Conditional: the step happens only sometimes (branching path)
            • 
            
          • Exception path: an error or workaround, not the happy path
            • 
            
          • Waste: shouldn't be needed (rework, duplicate effort, fixing someone else's mistake)
            • 
            
          • Automation candidate: this step could be replaced by a bot or integration
            • 
          
          
          
          Building phases manually
          
          
            
            
          1. Switch to Steps view.
            2. 
            
          2. Tick the checkbox on two or more step rows to multi-select them (or Ctrl+click the rows).
            3. 
            
          3. Switch to Phases view. The Group selected steps into phase button is now enabled.
            4. 
            
          4. Click it, give the phase a name. Done.
            5. 
          
          
        
          

        
          
          
          What a Process Template is
          
          
          A Process Template is a YAML file that says: "This is what Customer Onboarding looks like. It has three phases. The first phase has three steps. Here's how to recognize each step when you see it in a captured session."
          
          
          The Process Template view is where you open, edit, and test templates — click More ▾ at the top of the viewer, then Process Template. A sample template ships at normalization/canonical/sample-customer-onboarding-v3.yaml.
          
          
          Why bother
          
          
          Without a template, the viewer can only auto-suggest steps from interaction patterns. The names it picks are generic ("App: 4 actions"). With a template, every matched interaction gets the right name ("Search existing customer record"), groups into the right step, and the steps roll up into named phases. The PDD export, the step BPMN export, and the aggregate statistics all become hugely more useful.
          
          
          The minimal shape
          
          
          canonical_process:
  id: "customer-onboarding-v3"
  name: "Customer Onboarding"
  version: 7
  phases:
    - phase_id: "validate"
      name: "Validate customer"
      step_ids: ["check-crm", "credit-check"]
  steps:
    - step_id: "check-crm"
      name: "Check existing customer record"
      match:
        - process_name: "chrome.exe"
          window_title_regex: ".*Salesforce.*Search.*"
          interaction:
            control_type: "Edit"
            automation_id: "searchInput"
          
          
          Phases in a template
          
          
          A template's phases block groups its steps into milestones — the chunks an exec thinks in. Template phases drive the PDD export, the step CSV, and the phase-level BPMN. You don't have to hand-write the YAML: in the Template steps editor each step has a Phase dropdown — pick an existing phase or create one inline, and the phases block stays in sync. (This is separate from grouping one session's steps into phases, which you do in the Phases view.)
          
          
          Matching against a captured session
          
          
          From the Process Template tab, load the YAML, click Load sample session, and the match rate shows up. Aim for 80% or higher; below that you need to refine the match rules until they cover the real patterns the SME hit.
          
          
          Versioning + drift
          
          
          Templates have a version field. When you change a template and re-normalize old sessions, any step the analyst edited manually that now maps to a different template step gets a drift marker (you'll see a ⚠ icon in the Steps view). The aggregate Drift panel shows the trend across loaded sessions.

          Process map
          
          
            
            
          • Process diagram (BPMN) tab: the discovered process rendered as a standard BPMN diagram. Pan/zoom with mouse. Export the file (importable into Adonis, Bizagi, etc.) via the export button below.
            • 
            
          • Flow diagram tab: a network view showing how often each activity is followed by each other activity. Node with a green border = where sessions started; orange border = where sessions ended; edge thickness reflects how often that transition happened. Hover any node to highlight the session paths (variants) that run through it — everything off those paths dims so you can see where work diverges. Click a node to drill into every loaded session containing that activity, at the matching timestamp.
            • 
          
          
          
          Statistics
          
          
            
            
          • Activity frequency: SVG bar chart, top 12 by frequency. Hover the value to see total time.
            • 
            
          • Case durations: active duration (filled bar) with wall-clock as a thin overlay so you can spot heavy idle inside cases. Top 12 cases.
            • 
            
          • Trace variants: distinct activity sequences ranked by frequency. Top 80.
            • 
            
          • App outliers: apps appearing in <5% of cases - exceptions or misuse.
            • 
            
          • Repeated activities within a case: activities a worker did more than once inside the same case — often a sign of rework or fixing a mistake.
            • 
          
          
          
          Filtering
          
          
            
            
          • Text filter: substring match across activity chart, case chart, variants, outliers, and rework.
            • 
            
          • Date range: From / To date inputs filter the loaded sessions by their started_at field. The pills show "filtered from N" when a range is active.
            • 
          
          
          
          Exports
          
          
            
            
          • BPMN 2.0 XML / XES / stats.json: copy the per-session artifact from the first loaded session that has it.
            • 
            
          • Markdown report: a Confluence-friendly summary of the currently-filtered sessions (activity table, case table, top transitions). Use it as a paste-ready draft for a Process Definition Document.
            • 
            
          • App-category rule drafts: writes a YAML draft with one rule candidate per app that appears as "Unclassified" in the loaded sessions. Refine the labels and patterns, then add them to the team's central category rules.
            • 
          
          
        
          

        
          
          
          Running a capture session
          
          
            
            
          1. (One-time) Launch OBS with WebSocket enabled (Tools → WebSocket Server Settings → Enable, port 4455).
            2. 
            
          2. (Optional) Set PDT_CONFIG=path\to\your-config.yaml to load engagement-specific labels, hotkeys, OBS settings. See capture/sample-config.yaml.
            3. 
            
          3. Launch the capture tray app (npm start in capture/).
            4. 
            
          4. Right-click the tray icon → Start capture session. Or just press the start hotkey - the session auto-starts.
            5. 
            
          5. Show the status window (tray menu) for the live dashboard.
            6. 
            
          6. Fire markers as the SME walks through processes. End the session when done.
            7.

          Cancelling a long analysis
          
          
          Once an analysis kicks off the log host opens automatically. A red Cancel button in the log summary stops the in-flight Python child (graceful first, hard kill 500ms later). Works for single-session normalize, extended normalize, template match, and app vocabulary bootstrap. The aggregate Analyze all loop also has its own Cancel button.
          
        
          

        
          
          
          Common issues
          
          
          
            
          Normalization fails with "normalize.py not found"
          
            
          The viewer expects normalization/ as a sibling of viewer/ in dev, or under resources/normalization/ in a packaged build. Override with PDT_PYTHON if needed.
          

            
          "ModuleNotFoundError: pm4py" during normalization
          
            
          Run pip install -r normalization/requirements.txt against the Python interpreter the viewer uses.
          

            
          BPMN map shows "bpmn-js failed to load"
          
            
          The BPMN file is still on disk under the session folder - importable into Adonis directly. The in-viewer preview is a nice-to-have.
          

            
          No video in session view
          
            
          Capture ran without OBS, or the OBS recording path in manifest.json is unreachable. Timeline + statistics still work; click-to-seek is just a no-op.
          

            
          Empty event table
          
            
          Check the type checkboxes (activity / marker / system) and clear the text filter.
          

            
          Drill-down landed on a session but the wrong moment
          
            
          The drill uses a best-effort match on app/title to find the first activity event matching the label. For exact precision, click directly on the timeline bands.
          

            
          Hotkey didn't register in capture
          
            
          Another app may have the same global shortcut. Enable PDT_DEBUG=1 in the capture launch env and check %APPDATA%\process-discovery-tracker\boot.log for "hotkeys: start=false". Edit your config.yaml to use different keys.
          

            
          Citrix or remote-desktop session shows one band labelled "Citrix Workspace.exe"
          
            
          active-win cannot see inside Citrix windows from the local host. Either run the capture tracker inside the Citrix session, or accept that local capture will not classify inner apps and rely on markers + the OBS video for context.
          

            
          Multi-machine shift review: timelines from different workers do not line up
          
            
          Have each worker fire a sync marker (default Ctrl+Shift+Y in capture) at agreed moments with the same sync_id. The aggregate view uses these as alignment points.
          

            
          Aggregate report or app-category rule draft exports nothing useful
          
            
          Both work off analyzed sessions. Click "Analyze all sessions" first so every loaded session has stats.json. The rule draft needs at least one event classified as Unclassified - that means there is an app the team's category rules do not yet cover.
