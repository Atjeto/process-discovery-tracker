Process Discovery Tracker: Help

Capture side · v{{VERSION}}

What this app does

Polls the foreground window every 5 seconds and writes a per-session JSONL of window activity, runs, and system events. Optionally drives OBS to record the screen and writes a clock-sync file so the analyst's viewer can align timeline events with video.

Running a session

  1. (Optional) Launch OBS with WebSocket enabled. Tools → WebSocket Server Settings → Enable, port 4455. (You can also configure this from tray → Settings → Video/OBS.)
  2. (Optional) Tray → Session setup… to set the project code and task shortcuts for what you're about to record.
  3. Right-click the tray icon → Start capture session. Or just press the run hotkey: recording starts with your first run.
  4. Open the Live Session window from the tray to see what's being captured (or click the tray icon during a session).
  5. Press the run hotkey each time you begin the process: one press per run. Tray → End capture session when done; a short summary shows what was recorded.

Default hotkeys

Ctrl + Shift + S Start the next run (Run 1, Run 2, ...). Ends the previous run first. Starts recording if it isn't running yet.
Ctrl + Shift + E End the current run.
Ctrl + Shift + P Manual screenshot: annotated as screenshot_manual in the event stream.

All three are overridable in config.yaml under hotkeys:. The three are also surfaced in the hotkey overlay: a small click-through corner widget that stays visible across windows. Toggle from the tray (Show / hide hotkey overlay); visibility persists across launches.

Runs

A run is one pass through the process, from start to finish. Press the run hotkey at the start of each run: the app ends the previous run (if it is still open) and starts the next one, named Run 1, Run 2, and so on. Runs never overlap. Press the end hotkey when a run is finished, or simply start the next one. Ending the session also ends the open run.

If task shortcuts (process_labels) are set up for this engagement, they appear as named-run buttons in the Live Session window and under Start a named run in the tray. Each one starts a run with that name instead of a number.

Live Session window

The tray entry Show Live Session window opens a 460×720 always-on-top window that is the single live-session surface:

  • Start capture session button, shown while idle. Click it to begin a session; the run controls below dim until a session is running. (Starting a run also starts a session.)
  • Recording indicator + session timer
  • Currently-tracking app + title
  • The current run
  • Counters (events / runs / screenshots / interactions)
  • Recent-events feed
  • Start next run and End run buttons, plus named-run buttons when task shortcuts are set up
  • Inline end-session confirm: no browser dialog
  • When the session ends: a one-screen summary (runs recorded, duration, interactions, screenshots) with a Done button

First-run welcome

The first launch on a machine pops a welcome window with three buttons: Set up your profile (recommended first step), open the Live Session window, open this help. After dismissal it never re-pops automatically. Reopenable any time via tray → Help → Show welcome screen.

Multi-monitor screenshot

By default, screenshots follow the foreground display rather than always capturing the primary monitor. Override via screenshots.display in your config:

  • active (default): picks the display containing the focused window
  • primary: legacy behaviour, always the primary display
  • all: captures every display, emits one screenshot event per file with a _d<displayId>.jpg suffix

Tray menu (when a session is running)

  • Start next run: same as the run hotkey
  • Start a named run: submenu of process_labels entries (hidden when none configured)
  • End run: ends the current run
  • Manual screenshot: capture regardless of trigger config
  • Pause / Resume polling
  • End capture session: ends the open run, finalizes the manifest, stops OBS recording, then shows the session summary
  • Live status → Show / Hide Live Session window: toggle the always-on-top dashboard
  • Storage → Open sessions folder: jump to %APPDATA%\process-discovery-tracker\sessions\
  • Settings…: hotkeys, OBS, screenshots, storage limits (persists across sessions)
  • Profile…: worker identity stamped onto every recording

Configuration

Configuration is split into three places, by lifetime:

  • Settings (tray → Settings…), persistent across sessions: hotkeys, OBS, screenshots, storage / recording limits. Stored at userData/user-config.json and merged over any per-session YAML.
  • Profile (tray → Profile…): worker identity (id, display name, role, team). Stamped onto every recording's manifest.
  • Session setup (tray → Session setup…), per engagement: project code/name and task shortcuts. Stored at userData/quick-config.yaml.
  • Manual YAML (advanced): set PDT_CONFIG=path\to\config.yaml before launch for the full schema (process labels, hotkeys, OBS settings, idle thresholds, screenshot triggers, engagement metadata). See capture/sample-config.yaml in the repo. Settings / Profile still layer on top.

OBS recording: first-time setup (5 minutes)

OBS is optional but recommended. With OBS running, the capture app automatically starts a screen recording when you start a session, stops it when you end, and writes a tiny obs/sync.json file so the analyst's viewer can sync the timeline to the video.

  1. Install OBS Studio from obsproject.com (version 28 or later). One-time.
  2. Open OBS and go to Tools → WebSocket Server Settings.
  3. Tick "Enable WebSocket server". Leave the port at 4455. Leave authentication disabled for ease of use on internal machines (or set a password and copy it into your config's obs.websocket_password field). Click OK. OBS doesn't need a restart.
  4. Leave OBS running when you start a capture session. The tracker connects automatically, creates a scene named "Process Discovery -- Default" the first time, starts recording on session start, and stops on session end.

You don't need to click record in OBS yourself. The capture app does it. You also don't need to leave OBS in the foreground: minimize it after step 4 and you'll never need to look at it again unless you want to verify the recording.

OBS integration details

  • Connection: ws://127.0.0.1:4455 (localhost only). No network exposure.
  • Set obs.required: true in your per-session config to fail fast when OBS isn't reachable. Default is false so capture can run without OBS for ad-hoc testing.
  • First connection auto-creates a scene per config (default: "Process Discovery -- Default") with a timestamp overlay browser source. The burned-in clock helps you verify sync if anything ever drifts.
  • The recording's start timestamp and tracker↔OBS offset are written to obs/sync.json so the viewer can map any tracker event to a video seek position.
  • Where the video lands depends on OBS's own Settings → Output → Recording Path. The session's manifest.json records the absolute path so the analyst's viewer can find it after you move the session folder.

Output

Each session writes a self-contained folder under %APPDATA%\process-discovery-tracker\sessions\<engagement>\<YYYYMMDD-HHMMSS>\:

  • events.jsonl: one JSON event per line, append-only, the durable artifact
  • manifest.json: session metadata, status, OBS reference
  • config.yaml: snapshot of the config used
  • screenshots/: event-triggered captures
  • obs/sync.json: clock-sync data (if OBS was connected)

Citrix and remote desktop notes

The active-win library that powers polling has known limitations on Citrix: the foreground window is reported as the Citrix client, not the inner app. If your worker runs an app inside Citrix:

  • Run the capture tracker inside the Citrix session so it polls inner windows. Requires the Citrix profile to permit running unsigned Electron apps.
  • If that is not possible, run capture on the local machine; you will get one band labelled Citrix Workspace.exe for the duration. OBS still records the visible content. Mark every run with the run hotkey; classification of inner apps must be done by the analyst.
  • Validate behavior on a representative machine before scoping a Citrix-heavy engagement.

Storage retention

Sessions accumulate in %APPDATA%\process-discovery-tracker\sessions\ over time. The tray menu now shows the total count and disk usage, and offers two ways to clean up without leaving the app:

  • Per session: tray → Recent sessions → pick one → Delete... (confirms, deletes that single folder).
  • Bulk by age: tray → Prune sessions older than... → 30 / 90 / 365 days. Lists a sample of what will go, shows total bytes freed, confirms before deleting.

The currently-recording session can never be deleted from these menus. For the analyst side (with Python available), scripts/prune-sessions.py --older-than 90 [--apply] still works and supports --keep-recovered to skip orphan-recovered sessions that may need attention.

Troubleshooting

Hotkey didn't register
Another app may have the same global shortcut. Enable PDT_DEBUG=1 in the launch env and check %APPDATA%\process-discovery-tracker\boot.log for hotkeys: start=false. Edit your config.yaml to use different keys.
OBS won't connect
Make sure OBS is running with WebSocket Server enabled (Tools menu). Default port is 4455. If you enabled authentication, set obs.websocket_password in your config. Set obs.required: false to skip OBS entirely.
Tray icon doesn't appear at all
Enable PDT_DEBUG=1, relaunch, and check the boot log. Common causes: another instance already running (single-instance lock), missing tray icon file, antivirus blocking the executable.
Session shows up as "recovered" on next launch
The previous session ended without a clean close (crash, force-quit, power loss). Orphan sessions are auto-marked. A run that was still open stays open in events.jsonl; the analyst's tools close it at the end of the recording.
Where does my data go?
%APPDATA%\process-discovery-tracker\sessions\ on Windows. The tray has an "Open sessions folder" item.
BPMN export skipped during normalization
PM4Py's BPMN file writer invokes Graphviz dot for layout. Install Graphviz from graphviz.org and add its bin folder to PATH if you need BPMN files. The DFG view in the viewer renders without Graphviz; only the BPMN file generation requires it.
